Arman's ask: he transcribes restaurant-scale scans as-is (never a second "cookbook size" copy), and wants the site to compute a scaled-down cookbook quantity from that. He also wanted a curry recipe (resep-2, Ayam Kare) to visibly include its component paste recipe (resep-1, Bumbu Ayam Kare) rather than just naming it in the ingredient list.

**Schema (mirrors the Ingredient/MethodStep section-divider pattern):**
```ts
// Recipe — only set on batch/restaurant-scale recipes (the `scale` flag)
yield_amount?: number;  // what the batch as written produces, e.g. 20 (kg), 84 (orders)
yield_unit?: string;    // "kg", "orders" — whatever yield_amount is counted in

// Ingredient — this row IS a quantity of another recipe, not a raw item
recipe_ref?: string;    // id of the referenced Recipe
```
Convention (documented in code comments, not enforced): a row's `amount`/`unit` must be expressed in the same unit as the referenced recipe's `yield_unit`, so the site can divide to get a fraction — no general weight/count unit-bridging was built, since there's exactly one cross-reference pair in the cookbook so far and it wasn't worth the complexity.

**How the scale control works:** `ramayani`'s recipe page already had a dead serving-size stepper (`serves`/`baseServes`/`factor` state, gated on `typeof recipe.serves === 'number'`) built earlier but never reachable — the admin UI's Serves field is a plain text input, so `serves` was always a string on all 112 live recipes (confirmed via a live-data check before touching this). Rather than build a parallel mechanism, that dead stepper was repointed to `yield_amount`/`yield_unit` (renamed `qty`/`baseQty` for clarity) — `displayQuantity()`'s existing `factor` parameter in `units.ts` already did exactly the scaling math needed, unchanged. The control now defaults to the full batch as scanned (not an arbitrary "serves 4"), so the reader sees source-accurate quantities first and scales down from there — this required moving the `qty` useState to a lazy initializer keyed off `recipe.yield_amount` and adding an effect keyed on `id` to reset it on client-side recipe-to-recipe navigation (Previous/Next), since a plain `useRef` doesn't refresh across those.

**Sub-recipe rendering:** an ingredient row with `recipe_ref` gets a collapsible `<details>` block (native, no extra JS state) under its line, showing the referenced recipe's own ingredients scaled to `(row's parsed amount × this page's factor) / referencedRecipe.yield_amount`, plus a "View full recipe →" link. Scales together with the parent recipe's own stepper.

**Same fix surfaced a units.ts precision bug.** At extreme scale-downs (÷600), same-system amounts (imperial→imperial) never auto-picked a better-fitting unit — `displayQuantity()` only ran the base-unit auto-pick (`pickWeightUnit`/`pickVolumeUnit`) when crossing metric↔imperial. **2026-08-26/27 — the batch-sauce-to-home-scale conversion playbook.** Once a sauce/paste's `yield_amount` is a real physical unit (the full restaurant batch), the site has nothing smaller to show a home cook — so a genuine home-scale twin recipe is needed, following the same `recipe_type`/`linked_recipe_id` batch/home split used for whole dishes (resep-2→113, resep-4→114, resep-8→115, resep-45→117). Done twice so far: resep-5→resep-118 (Ayam Bumbu Rujak Sauce, 2026-08-26) and resep-10→resep-120 (Ayam Sauce Ramayani Sauce, 2026-08-27). **Reuse this exact checklist for the next one:**

1. Confirm the real batch total already exists (weight/volume derived from the ingredient list, documented in the batch recipe's own `review_notes`) — prerequisite, do this first if missing.
2. Target yield: **"about 4 cups"**, a standing default reused across sauces, not re-derived per recipe.
3. Rescale every ingredient by (target ÷ batch total), then round to practical kitchen units (real retail can/box sizes, clean tsp/tbsp/cup fractions) — not exact fractions. Merge rows that only differ because of the restaurant's own measuring tool (resep-10's two canting-based oil lines became one "vegetable oil" row).
4. Where an original quantity used an ambiguous/unresolved unit (an unconfirmed terasi "piece" size, a "bowl", a "container"), resolve by normal-home-quantity judgment rather than scaling an unknown, and say so explicitly in `review_notes` — don't silently launder the uncertainty away.
5. Shorten method timings for the smaller volume instead of copying restaurant-scale timing verbatim. If the batch recipe has **no method at all** (resep-10's case — "method to be confirmed with Hertha"), the home version inherits that same gap rather than inventing a technique from nothing.
6. Headnote: Test Kitchen-style framing — "Makes about 4 cups — enough for about N orders (about 1 cup per order)." The "~1 cup per order" figure itself is a standing convention (Arman's call, 2026-08-26, replacing an earlier more precise-looking ~90g/order estimate) — reuse it, don't re-derive per-sauce precision.
7. New recipe: `recipe_type: "home"`, `linked_recipe_id` → the batch id, category matches the batch's, `yield_amount: 4, yield_unit: "cups"`.
8. Archive the batch: `recipe_type: "batch"`, `linked_recipe_id` → the new home id, one `review_notes` line noting it's now frozen. No other edits to it, ever again.
9. **Check whether any existing recipe already has a `recipe_ref` pointing at the batch recipe, and repoint it to the new home id.** resep-116 pointed straight at resep-10; once resep-10 was archived (hidden from the public site), that link would dead-end unless repointed. This step didn't apply to resep-5→118 (nothing referenced resep-5 yet) but will apply whenever a dish already exists on top of the sauce being converted — always check for this.

**Does this generalize to whole dishes (not sauces)?** The *serving-derivation* methodology (items 1-6 below) doesn't — a sauce/paste is one blended, undifferentiated mixture, which is exactly what makes "pick a cup target, rescale everything proportionally, round" work cleanly. A whole dish has discrete count-based ingredients (a chicken, an egg, a pan) that can't be fractionally scaled, and its liquid/solid ratios and cooking times don't scale linearly with batch size (evaporation, pot geometry, coverage all behave differently at 1/50th scale). The dataset has two different, working patterns for dish conversions instead — reuse whichever fits, not the cups playbook:
- **Clean-divisor pattern** (resep-4→114, resep-8→115, resep-45→117, resep-6→resep-122): the batch recipe's primary ingredient count already divides evenly into a home-usable unit (÷7 whole chickens → 1 chicken, ÷9 pans → 1 pan, ÷4 game hens → 1 hen) — divide everything else by that same integer.
- **Real-anchor pattern** (resep-2→113): the batch's own text states a real per-order fact (e.g. "4.5 lb balls of 6 orders each" → ¾ lb chicken/order) — anchor the protein portion to that stated fact directly rather than computing a division, then adjust liquid/paste amounts by cooking judgment for small-batch scale rather than pure linear scaling.

**But items 7/8 (the floor-check and re-sum) ARE universal — they're about how the site's stepper/rounding math works, not about sauce chemistry, so apply them to a dish conversion too.** Divide every ingredient by the chosen integer, then check each one against the site's ¼-tsp (volume) / no-floor (count units like "clove") rounding behavior before calling it done, and re-sum to sanity-check the total. Items 9/10 (the fixed-minimum-batch-size and size-to-exactly-what's-needed rules) are sauce/paste-specific in their *number* (4oz/½cup) but the *reasoning* transfers directly: for a dish, "1 whole [protein unit]" (1 chicken, 1 hen, 1 pan) is usually *already* the natural realistic minimum — you're not choosing a batch size, the protein count picks it for you — so item 10's logic ("if what's needed already clears a sensible floor, just size to exactly that, don't invent a bigger batch") is the one that actually applies most often to dishes, not item 9.

## Canonical yield-to-servings methodology (locked in 2026-08-27 — read this section, not the chronological trail above, for how to do this going forward)

Confirmed explicitly with Arman after getting it wrong twice (the sauces' first-pass `yield_per_serving: 1`, then resep-121's first-pass `yield_per_serving: 18`). Both mistakes were the same mistake: treating "amount per dish-portion/order" as if it were "amount per real person."

1. **`yield_amount`/`yield_unit` is exact and objective** — the real physical quantity a sauce/paste/marinade produces. Never adjusted to make anything "come out even" with a servings count.
2. **`yield_per_serving` is subjective, and it must be derived from the dish that uses the sauce/paste — never invented by looking at the sauce/paste alone.** "The driver will be the dish recipe, not the sauce or paste recipe" (Arman, verbatim). Concretely, get two facts from the *dish*:
   - **(a)** the dish's own stated amount of the sauce/paste per one dish-portion (e.g. resep-116: "1 cup sauce" per order; resep-113: "1 tbsp paste" per order — read directly off the dish's ingredient line, not guessed).
   - **(b)** how many real people that same dish-portion feeds (e.g. resep-116's `serves: "2-3"`; resep-113's `serves: "1-2"`) — this is itself a judgment call belonging to the *dish* recipe's own `serves` field, not something to re-derive at the sauce/paste level.
   - `yield_per_serving = (a) / (b)`, using the midpoint of (b) if it's a range. This is a genuine division, not a copy — copying (a) alone straight into `yield_per_serving` is the exact mistake made twice.
3. **Scaling the sauce/paste up to a practical batch size**: take the dish's *whole* base unit — paste amount, dish-portions, and people-fed together — and multiply all three by the same integer K. Don't invent a batch size disconnected from the dish's own ratio. Sanity-check the *result* on both ends: too small a K makes ingredients unmeasurable (sub-teaspoon, fractions of a whole clove); too large a K implies feeding an unrealistic number of people from one batch. If K forced by "whole units only" (e.g. needing whole garlic cloves) lands on an unrealistic number of people fed, the fix is usually to **accept a fractional aromatic** (½ clove, 1½ candlenuts) at a smaller, more realistic K — not to keep growing the batch. Ask the person actually cooking whether fractional units are acceptable; don't assume either way.
4. **This is unrelated to whether the *dish itself* also needs a `serves` correction.** Both resep-116 and resep-113 had their `serves` field corrected as part of this exercise (4→2-3, 1→1-2) — those were real fixes to guesses that predated this methodology, not new estimates invented to make the math work. If a dish's own `serves` value looks unexamined, that's worth revisiting *before* trusting it as input (a), not after.
5. **Units in home-scale recipes should stay kitchen-plain** (tsp/Tbsp/cups), never grams, and never vague qualifiers like "heaping."
6. **`yield_unit` must exactly match the unit the *dish's own ingredient line* already uses for this sauce/paste — not whichever unit makes `yield_per_serving` a clean number.** Got this backwards once: set resep-121's `yield_unit` to "tsp" specifically so `yield_per_serving` would be a whole number (2), while resep-113's own ingredient line said "1 **tbsp**" — a reader clicking through hit a jarring, needless unit mismatch (12 tsp vs. 4 Tbsp is the same amount, but doesn't *read* the same). `yield_per_serving` is never shown to a reader directly — only the computed "≈N servings" text is — so it's the field that should absorb an ugly decimal (0.667), never the visible `yield_unit`. Rule of thumb: **match the dish's unit first, then let `yield_per_serving` be whatever decimal falls out** — not the other way around.
7. **Every ingredient's full-batch amount must survive being divided down to 1 dish-portion without rounding to zero — and this is NOT a batch-size (K) problem, so don't try to fix it by resizing the batch.** The site's scaling stepper rounds every tsp-based ingredient to the nearest ¼ tsp. Viewing the recipe at its smallest meaningful setting (1 unit of `yield_unit` = exactly 1 dish-portion, by design) divides every ingredient by K. If a full-batch amount is below K × ¼ tsp, it rounds to zero and silently disappears from the ingredient list at that view — and this happens *regardless of how big K is*, since the fixed per-dish-portion ratio doesn't change no matter how large the stored full batch is (resep-121 hit this at K=4: ginger/turmeric/MSG at ¼ tsp full-batch became 1/16 tsp per portion, well under the floor). **The fix is to raise the smallest ingredients up to K × ¼ tsp (the minimum that survives division), not to change K.** This is a real increase beyond the mathematically "precise" scaled ratio — flag it plainly when it happens, since it can be a meaningful flavor shift (resep-121's fix roughly quadrupled ginger/turmeric relative to pure proportional scaling). Check this for every small-quantity ingredient whenever setting up a new batch — sugar/salt/oil are usually fine since they start larger; ginger/turmeric/MSG/kencur-style small aromatics are the ones that typically need the floor applied.
8. **After any floor-fix (item 7), re-sum the whole ingredient list and sanity-check it against the stated `yield_amount` — don't assume fixing individual ingredients in isolation keeps the total consistent.** Missed this on resep-121: floor-fixed several tiny ingredients one at a time (item 7) without re-checking the total, and separately one "clean-looking" full-batch number (onion, rounded to "¼ cup" without checking it against the real per-portion ratio) had silently drifted 63% high from an earlier pass. The combined effect: summing the recipe's own ingredients came to roughly 1.5–2x the stated yield — caught only when Arman actually added it up by eye from a screenshot. **The check that would have caught this immediately:** compute the *true, scale-invariant per-single-dish-portion amount* for every ingredient directly from the original restaurant batch (total ingredient amount ÷ total batch's implied dish-portion count — independent of whatever K you're using for the current draft), and compare each stored value against it. Expect the summed total to run somewhat *higher* than the stated finished yield (raw ingredients shrink during cooking/blending — resep-121 settled at ~53% higher raw, a ~34% cook-down, which is normal and worth stating plainly) — but a gap far beyond a plausible shrinkage amount (resep-121's was ~150%+ before the fix) means a real arithmetic error, not shrinkage. Run this check as a matter of course after any round of floor-fixing, not only when someone happens to notice by eye.
9. **Standing minimum batch size, adopted 2026-08-27, supersedes deriving K from servings-count reasoning: 4 oz / 8 Tbsp / ½ cup is the smallest jar of anything to make, full stop.** All of items 2/6/7/8 above came from trying to size a batch by working backward from "how many real people should this feed" — Arman eventually cut through that entirely: don't derive K from servings math at all, just target this fixed floor directly, every time. Reasoning for the specific number: 4oz is a real, recognizable "smallest jar" size (matches common spice/condiment packaging), and it's simple enough to apply with zero per-recipe judgment calls. **How to apply:** compute the true per-dish-portion ratio for every ingredient (item 8's method), scale everything up to hit this floor (not to hit some serving-count target), and let the resulting "makes about N orders / ≈M servings" be *reported*, not engineered backward. If a smaller batch (e.g. half this size) was already built and its floor-fixed ingredients need to double to reach 4oz, doubling is exact and safe — per-dish-portion amounts are scale-invariant under uniformly doubling both the batch and its implied order-count together (verified on resep-121: every floor value landed on the identical per-portion amount at the doubled size). Doubling small counts also conveniently tends to turn awkward fractions (½ clove) into clean whole numbers (4 cloves) — a nice side effect, not something to engineer for specifically. **This floor is a minimum, not a target to hit exactly.** Originally noted resep-118/resep-120 (already at 4 cups each) as clearing the floor comfortably and not needing revisiting — **that turned out to be wrong for resep-120, see item 10.**
10. **If what one order needs is already above the standing floor (item 9), just size the whole recipe to exactly that amount — don't build a bigger batch "for good measure."** Found 2026-08-27, same day as item 9: resep-120's "makes 4 cups, enough for 4 orders" framing was never actually checked against the true per-order ratio from resep-10's original ingredients — it turned out 4 cups is really ~7 true orders' worth, not 4 (the ingredient math itself was internally consistent, ~955ml summed against a 946ml/4-cup target; the *order-count claim* was the error, found by computing the true per-order total directly the same way item 8 describes). Rather than fix the mismatched order-count claim, resized the recipe to exactly 1 cup — what resep-116's own ingredient line actually needs, and already comfortably above the ½-cup floor. **This is better than picking any bigger batch size, for a structural reason, not just simplicity:** when a recipe's default view already equals exactly what one order needs, the stepper only ever needs to scale *up* from there (a bigger batch), never *down* to view a single order — so the ¼-tsp division-rounding-to-zero problem (items 7/8, the entire reason resep-121 needed multiple rounds of floor-fixing) structurally cannot occur on this recipe at all. Only one ingredient (MSG, true value 0.0625 tsp) needed a floor-bump (to ⅛ tsp) even at this 1-cup size — far less friction than resep-121's batch-then-divide approach needed. **Rule: check whether one order's real per-order amount already clears the standing floor before building any bigger batch — if it does, size to exactly that and stop.** Only reach for a bigger multiple (item 9's approach) when the true per-order amount itself is below the floor.

## New pattern (2026-08-27): back-solving a missing batch count from total volume/weight against an external reference

Two conversions (resep-11 Ayam Solo -> resep-123; resep-14 Ikan Acar & Pepes -> resep-124/resep-125) had no stated protein count, weight, or yield anywhere on the source scan — nothing to anchor a divisor to at all, unlike the clean-divisor dishes (which had an explicit "20 ekor Ayam") or the sauces (which had a real batch total to target 4 cups from). Arman's rule, stated explicitly: **calculate total volume/weight of the thing that scales (the braising liquid, the spice paste), compare it to an external reference's per-unit amount for the same thing, back-solve the implied unit count, then divide the BATCH'S OWN ingredients by that count — never substitute the reference's own ratios for the batch's.** The reference is a ruler for sizing, not a recipe to copy. This mirrors item 3 above (dish-driven scaling) but for cases with no dish-portion fact to read at all, only an external norm.

- **Ayam Solo (2026-08-27):** batch's only volume fact was "1500cc water." Reference: ~500mL water per whole chicken (chopped, tightly packed). 1500/500 = 3 chickens exactly, and every other ingredient in the batch divided into a clean, plausible amount at ÷3 (1 cup kecap manis, 1 cup sugar, ~7 kaffir lime leaves) — strong convergence, high confidence.
- **Ikan Acar & Pepes (2026-08-27):** batch's spice-paste ingredients (chili+candlenut+shallot+garlic+ginger+salt+MSG+sugar) summed to ~4037g. Reference gave per-fish piece counts (4-5 shallots, 2-3 garlic, 3-4 candlenuts, etc.), converted to grams using typical piece-weight estimates (~12g/shallot, ~4g/garlic clove, ~4.5g/candlenut, ~12g/chili) for a ~141g/fish reference total. 4037/141 ≈ 28.6, rounded to 28 fish. **Individual-ingredient implied counts did NOT converge here** (ranged ~10 to ~67 across ingredients, a ~6x spread) — meaning Ramayani's own recipe is proportionally much heavier on candlenut/salt/sugar and lighter on garlic than the generic reference. That's expected, not an error: **only use the aggregate total to find the batch count; keep dividing the batch's own per-ingredient amounts by that single count regardless of whether individual ingredients "agree" with the reference** — convergence across ingredients (like Ayam Solo had) is a nice confidence booster when it happens, but its absence doesn't invalidate the method, since the whole point is preserving the restaurant's own flavor ratios, not conforming to a generic one.
- **Independent cross-checks are valuable when something in the batch wasn't used to derive the count.** Ikan Acar's tomato (2000g, kept separate from the spice-paste total since the reference categorizes tomato as "aromatic layering" not "spice paste") divided by the same 28 landed on ~71g/fish — closely matching the reference's own "½ medium tomato" independently. When an ingredient excluded from the back-solve math still lands near the reference at the chosen count, that's a genuine (not circular) confidence check — look for one if possible.
- **A reference recipe can supply ingredients the batch never recorded at all — add those only where the dish structurally requires them, and flag clearly.** Pepes traditionally requires banana leaf + kemangi + lemongrass + salam + kaffir lime leaves; resep-14's scan never quantified any of them even though its own method mentions the banana-leaf wrap. Since there's no Ramayani-specific quantity to scale down for these, they were added straight from the reference's per-fish amounts into resep-125 (Pepes) only, not resep-124 (Acar, which doesn't use them) — clearly noted in review_notes as reference-sourced, not scan-derived. Don't add reference ingredients to a dish that doesn't call for them just because they appeared in the same reference table.
- **One batch can split into more than one home dish when it's really a shared spice paste used two different ways.** resep-14 covered two distinct final preparations (fried/pickled Acar vs. banana-leaf-wrapped/steamed Pepes) off one shared bumbu. Built two separate home recipes (resep-124, resep-125), each with the full shared spice-paste ingredient list repeated (not factored out into a third cross-referenced paste recipe — recipe_ref/yield_amount machinery is overkill when both dishes need the identical paste at an identical 1:1 scale, no batch-vs-dish ratio to compute). **`linked_recipe_id` is a single string field (confirmed by reading `src/types/recipe.ts` — not rendered anywhere on the site, pure data bookkeeping)** — it can't point at two homes from one batch, so resep-14 was left with `linked_recipe_id` unset and both new ids noted in its own review_notes instead of picking one arbitrarily as "primary."

## New pattern (2026-08-29): multi-tier "factory chain" dishes — store every real tier, build ONE home recipe

The Excel-prep-sheet workflow (Satay, SGTB, Otak Otak, Gule Kambing, and the `Factory Cook -`/`Factory Mix -` sheets behind them — see [[raspberry-master-spreadsheet]]) surfaced a genuinely new shape: a dish built from a **chain** of factory components (e.g. California Chili Paste → Satay Sauce Base → Satay Sauce → Satay), not a single batch→home pair. Arman's explicit rule, confirmed 2026-08-29:

1. **Every real factory/restaurant-batch tier gets stored as its own recipe** — mirroring the master spreadsheet's own sheet structure 1:1 (one raspberry recipe per `Factory Cook -`/`Factory Mix -` sheet, plus the main dish sheet). This holds even when nothing else `recipe_ref`s a given tier directly except the next tier up in the chain — the point is traceability, not just what's strictly load-bearing. This is also the direct fix for a real failure mode found the same day: SGTB's coconut milk was undercounted (98 vs. the correct 196 fl oz) specifically because the tier between the paste and the home dish existed only as prose arithmetic in a `review_notes` field, with no stored recipe to check the math against. See `resep-144` (added specifically to close that gap) and `raspberry/derivations/AUDIT.md` for the incident.
2. **The home-facing recipe is ONE recipe, decomposed all the way down to raw ingredients — not a parallel home twin for every intermediate tier.** Don't build "Satay Sauce Base (home)" *and* "Satay Sauce (home)" *and* "Satay (home)" as three separate entries; expand the whole chain's raw ingredients (unpacking "1 bag of X" into its fractional share of X's own ingredient list, recursively) and apply one consistent scaling fraction across the lot, same as `resep-140` (Satay Sauce) and the corrected `cs-sambal-goreng-tahu-buncis` both do. A tier consumed only by the next tier up (a paste that's always cooked into a base, a base that's always cooked into a final sauce) doesn't need its own home-scale sibling — nobody wants to shop for 1/200th of a factory chili paste on its own.
3. **Exception: a component genuinely reused by more than one dish stays standalone.** If two or more dishes actually call for the same sauce/paste at the point where a home cook would use it (not just share an intermediate factory tier) — e.g. Satay Sauce also feeding Gado Gado, per the same source sheet — keep it as its own home recipe (`resep-140`-style), `recipe_ref`'d from each dish that needs it, rather than duplicating its derivation math into every dish that uses it. The dividing line: is this something a home cook would ever want to make *on its own* and keep on hand for more than one thing? If yes, standalone. If it only ever exists as an input to exactly one further dish, fold it in.
4. **Read the master spreadsheet directly for every tier**, rather than transcribing pasted text by hand — eliminates a whole class of copy-paste risk, and is strictly more reliable now that it's known to exist. See [[raspberry-master-spreadsheet]] for the file location, the sheet-naming convention, and the `BOX × QTY/BOX = total` column rule (including its one real trap: a BOX number that's redundantly echoed inside the DESCRIPTION's own parenthetical — e.g. `2 | 98 | fl oz | (2 large cans)` — is still a real multiplier, confirmed against `resep-2`'s original scan; don't mistake that redundancy for a stray non-multiplying artifact, a mistake made once and reversed the same day).
5. **Keep the actual derivation computation as a committed, re-runnable script** (`raspberry/derivations/*.py`), not a throwaway — this is what makes the numbers checkable later instead of trusted on faith. `raspberry/derivations/AUDIT.md` tracks every batch→home pair's verification status; extend it rather than starting a parallel tracking scheme.
